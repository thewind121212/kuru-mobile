# Auth chrome continuous experience — design spec

**Date:** 2026-05-17
**Tag candidate:** `v0.2.1-auth-chrome-continuous`
**Status:** approved by user 2026-05-17

## Why this exists

Cold-launching the app on a simulator currently shows ~1–2 s of solid white before the login screen appears. The branded splash (`SplashScreen` + `AuthLogo` + `AuthBackdrop`) is implemented but the user never perceives it, because:

1. **iOS native LaunchScreen is unbranded.** `ios/Runner/Base.lproj/LaunchScreen.storyboard:19` references an image asset `LaunchImage` that resolves to the Flutter-template default — three 1×1 transparent PNGs in `ios/Runner/Assets.xcassets/LaunchImage.imageset/`. The storyboard's `backgroundColor` is hardcoded white. iOS shows this *before Flutter starts*, so during the ~1–2 s of engine boot the user sees a plain white screen.
2. **Flutter `/splash` route flashes by.** Bootstrap on localhost completes in ~50–300 ms, so even though `SplashScreen` renders correctly, it's gone before a human eye registers it.
3. **App icon is the Flutter default.** `ios/Runner/Assets.xcassets/AppIcon.appiconset/` contains the `flutter create` template's blue "F" PNGs (verified by `ls -la` showing all files dated to the original `flutter create` run). The iPhone home screen shows the Flutter logo, not the kuru logo.

Goal: a continuous branded experience from icon tap to first interactive screen — same logo, same background, no white flash, no Flutter "F" anywhere.

## Architecture

### The three splash surfaces (clarified)

```
[tap icon]
    │
    ▼
┌─────────────────────────────────┐
│ Layer 1: Native LaunchScreen    │  iOS storyboard / Android launch_background.xml
│   - Pure native, no Dart        │  Shown by the OS before Flutter starts.
│   - Static image + bg color     │  Duration: ~200ms release, ~1–2s debug
│   - GENERATED by                │
│     flutter_native_splash       │
└─────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────┐
│ Layer 2: Flutter /splash route  │  lib/features/splash/splash_screen.dart
│   - AuthBackdrop (3 orbs anim)  │  Triggers appBootstrapProvider.
│   - AuthLogo (glow + sparkles)  │  Min display: 800ms (new)
│   - Spinner + tagline           │
└─────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────┐
│ Layer 3: Next screen            │  Onboarding / login / totp / create-org / org-picker / home
└─────────────────────────────────┘
```

Continuity rule: layer 1's background color = layer 2's `pageBg` (indigo light `#F3F6FF` / indigo dark `#080814`). Layer 1's logo is a static rendering of the same kuru wordmark used in `AuthLogo`. The transition between layers should feel like the logo "wakes up" (static → glow animation begins) rather than a jump cut.

### Why this approach (vs alternatives considered)

- **Why `flutter_native_splash` over manual storyboard edit:** the manual route requires hand-authoring 1×/2×/3× PNGs, editing the storyboard XML, doing the equivalent for Android `launch_background.xml`, AND handling the separate Android 12+ splash API (which uses `windowSplashScreenAnimatedIcon` rather than the older drawable). One generator, one config, one command keeps it maintainable.
- **Why `flutter_launcher_icons` over manual icon authoring:** same logic. iOS needs ~15 sizes; Android needs 5 mipmap densities plus an adaptive icon (foreground + background layer). Generator handles all of it from a single source.
- **Why a minimum display time over no change to Flutter splash:** without it, on a healthy localhost backend the splash route renders for ~50 ms — visually undetectable. The min display time guarantees the user sees the brand even on fast paths, and degrades gracefully if bootstrap is slow (no artificial cap, just a floor).

## Components

### 1. App icon — `flutter_launcher_icons`

**Source:** `assets/logo.webp` (1280×1280, confirmed via `sips`).

**Pubspec config (added to dev_dependencies + a new top-level `flutter_launcher_icons:` block):**

```yaml
dev_dependencies:
  flutter_launcher_icons: ^0.14.1   # or latest at implementation time

flutter_launcher_icons:
  image_path: "assets/logo.webp"
  ios: true
  android: true
  remove_alpha_ios: true            # App Store rejects icons with alpha
  adaptive_icon_background: "#080814"   # indigo-dark pageBg, matches splash bg
  adaptive_icon_foreground: "assets/logo.webp"
  # Optional, deferred: min_sdk_android, web, windows, macos
```

**Generated files (committed to git):**
- `ios/Runner/Assets.xcassets/AppIcon.appiconset/Icon-App-*.png` (regenerated)
- `android/app/src/main/res/mipmap-*/ic_launcher.png` (regenerated)
- `android/app/src/main/res/mipmap-anydpi-v26/ic_launcher.xml` (new adaptive)
- `android/app/src/main/res/values/colors.xml` (adaptive bg color)

**Command:** `dart run flutter_launcher_icons`

**Open question — alpha:** `logo.webp` may have a transparent background. `remove_alpha_ios: true` flattens it onto white, which clashes with our dark-mode aesthetic. If the logo IS transparent, we should either (a) pre-bake a solid `#080814` background into a copy of the source, or (b) override `image_path_ios` with that pre-baked variant. Decide at implementation time after inspecting the alpha channel.

### 3. Flutter splash minimum display time

**File:** `lib/features/splash/splash_screen.dart`

**Change:** wrap the bootstrap watch so the splash route holds for at least 800 ms even after bootstrap resolves. Design sketch — final shape settles during TDD, but the shape is:

```dart
final _splashStartProvider = StateProvider<DateTime>(
  (ref) => DateTime.now(),
);

final _splashGateProvider = FutureProvider<BootstrapResult>((ref) async {
  final start = ref.read(_splashStartProvider);
  final boot = await ref.watch(appBootstrapProvider.future);
  final elapsed = DateTime.now().difference(start);
  const minSplash = Duration(milliseconds: 800);
  if (elapsed < minSplash) {
    await Future<void>.delayed(minSplash - elapsed);
  }
  return boot;
});
```

The router redirect reads `_splashGateProvider` instead of `appBootstrapProvider`. If bootstrap takes >800 ms, no artificial delay. If it takes <800 ms (the common case), the splash holds until the floor.

**Edge case — bootstrap error:** today the redirect routes to `/login` on error. The gate provider must propagate the error (don't swallow), and the redirect's `error:` branch keeps working.

**Edge case — hot restart:** the splash provider re-evaluates on hot restart (R). That's fine — same path as cold start.

### 4. Password show/hide eye toggle on `KFormField`

**File:** `lib/design/widgets/k_form_field.dart`

**Change:** `KFormField` becomes a `StatefulWidget` (currently `StatelessWidget`). When `obscureText: true`, render a trailing `IconButton` (Material `IconButton`, not `KIconBtn` — this is the glass aesthetic, not flat). Icon = `Icons.visibility_outlined` when text is hidden, `Icons.visibility_off_outlined` when shown. Tapping toggles a private `_revealed` flag.

**API change:** the public constructor signature is unchanged. The `obscureText` parameter keeps its semantics (initial state = obscured when true). Callers don't need to change. Login + Register screens get the toggle for free.

**Accessibility:** the IconButton needs a `tooltip` and a localized semanticsLabel that says "Show password" / "Hide password" (add to `app_en.arb` + `app_vi.arb`). The whole point is that this is interactive — assistive tech users need to find it.

**Visual constraints:**
- Icon size 18 (matches the leading icon size in the existing layout).
- Color = `c.textMuted` normally, `c.textSecondary` on press (use `MaterialState`).
- The button must not push the existing `errorText` slot down — the height should sit inside the existing 6 px vertical padding of the KGlass row.
- Tap target must still be ≥ 32 px even though the icon is 18 px — `IconButton` defaults to 48; we'll override to 32 with `constraints: BoxConstraints.tightFor(width: 32, height: 32)` + `padding: EdgeInsets.zero`.

### 5. AuthLogo polish — deferred

Current `AuthLogo` (`lib/design/auth/auth_logo.dart`) implements: glow animation (3s cycle), dual ambient shadows, two sparkle accents, glass border. No specific complaint from the user. Touching this without a goal risks regression of the v0.2.0 visual that was already approved. Revisit only when there's a concrete request (e.g., "the glow is too aggressive at night," "the sparkles distract from the wordmark").

## Data flow

```
[cold launch]
    OS shows LaunchScreen.storyboard (native, no Dart yet)
       │
       │ Flutter engine boots, Dart VM loads, first frame renders
       ▼
GoRouter initialLocation: '/splash'
    SplashScreen.build()
       │
       │ ref.watch(_splashGateProvider) starts the wrapped bootstrap
       ▼
appBootstrapProvider runs (SuperTokens session check + /api/v1/profile/GetUserInfo)
       │
       │ resolves with BootstrapResult
       ▼
_splashGateProvider awaits min-splash floor (800ms minus elapsed)
       │
       │ resolves
       ▼
_BootstrapNotifier fires → router re-evaluates redirect → routes to next screen
```

The native LaunchScreen → Flutter splash transition is handled by Flutter Engine; we don't control its timing directly. The flutter_native_splash docs note that the LaunchScreen image is also briefly shown by the engine as the first Flutter frame, which gives a smooth visual handoff into the Dart splash.

## Error handling

| Scenario | Behavior |
|---|---|
| Bootstrap returns error (e.g., backend down) | `appBootstrapProvider` rethrows. `_splashGateProvider` propagates the error after the min-splash floor (no swallowing). Router redirects to `/login`. |
| Network timeout during bootstrap | dio's existing timeout handling fires; treated as ApiFailure; bootstrap returns `BootstrapUnauthed`. User lands on `/login` after the min-splash floor. |
| Bootstrap takes longer than 800 ms | No artificial delay; splash holds until bootstrap completes naturally. |
| `flutter_launcher_icons` source file has alpha and App Store would reject | `remove_alpha_ios: true` flattens onto white. We may need to pre-bake the logo over `#080814` if the white flatten looks wrong. |
| Splash widget rebuilt mid-flow (theme change, locale change) | `_splashStartProvider` is a StateProvider — its value sticks for the session, so rebuild doesn't reset the min-splash timer. |

## Testing strategy

### Unit / widget tests

- `test/design/widgets/k_form_field_test.dart` — new test cases for eye toggle:
  - Renders no toggle when `obscureText: false`
  - Renders toggle when `obscureText: true`, icon defaults to `visibility_outlined`
  - Tap flips to `visibility_off_outlined`, second tap flips back
  - Underlying `TextField.obscureText` mirrors the toggle state
  - Tooltip / semanticsLabel localized correctly (test in vi locale)
- `test/features/splash/splash_screen_test.dart` — new tests for the gate:
  - When bootstrap resolves in <800 ms, splash holds until 800 ms then redirects
  - When bootstrap resolves in >800 ms (fake via override), splash redirects immediately on resolution (no extra delay)
  - When bootstrap errors, error propagates after the floor

### Manual verification

- iOS simulator cold launch (iPhone 16, debug + release): logo visible on indigo background from icon-tap through to login. No white flash.
- Android emulator cold launch: same.
- iOS dark mode: native splash uses dark background. Flutter splash matches.
- Login screen password field: eye icon toggles correctly.
- Register screen password field (and password-confirm): eye icon present on both.
- Home screen icon (after install): kuru logo on home grid, not Flutter "F".
- `flutter analyze` exits 0.
- `flutter test` passes (existing 136 + new tests).

### What we can't easily automate

- Native splash visual correctness (no easy way to widget-test the iOS storyboard / Android launch_background). Verify manually in simulator screenshots.
- App icon rendering on physical device home screen — verify on at least one real iPhone before tagging the release.

## Implementation notes / build order

Recommend this order in the implementation plan:

1. **Eye toggle first** (smallest, most isolated, pure Dart, TDD-friendly).
2. **Splash min display time** (still pure Dart, easy to test in isolation).
3. **App icon generation** (run generator, commit output, manual verify on simulator).
4. **Native splash generation** (same pattern, commit output, manual verify).

Reason: 1 and 2 are pure-Dart logic changes — they can land independently and be merged even if 3/4 reveal asset issues. 3 and 4 touch generated platform files, which is harder to revert cleanly.

**Native-plugin gotcha (from CLAUDE.md):** `flutter_native_splash` and `flutter_launcher_icons` are pure Dart code generators — no native plugin code. The standard `flutter clean && pod install` dance is NOT required. Hot-reload won't show the new native splash (it's a build-time artifact), so after running each generator, do a full `flutter run` cold restart from terminal, not `R` from inside the running session.

## Out of scope (do not do)

- AuthLogo polish — deferred, see Component 5.
- Adding a flutter native splash animation (Android 12+ supports animated splash; we use static for now to match iOS parity).
- Replacing the source logo asset — `assets/logo.webp` stays as-is.
- Theme palette changes — indigo is the default and stays default.
- Web / desktop platform icons — neither is in the v1 scope (mobile only).
- Pre-loading any data in the splash beyond bootstrap.
- Configuring `flutter_native_splash`'s `branding` image (the Android 12 footer logo). Possible v0.3+ enhancement.
